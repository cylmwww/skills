# 架构与工程设计学习规划

## 目标与边界

把一个真实项目转化为可执行的架构学习计划。学习成果是理解模块职责、数据与状态流、信任边界、失败处理和设计取舍，并能把这些认识迁移到新需求。

默认由 coding agent 负责源码定位、代码生成、配置、实验搭建、调试及图文初稿；学习者负责提出问题、预测行为、审阅证据、比较方案和作出设计决定。不要要求手写源码、重写核心循环、背诵 API 或通读大文件。用户明确要求实现训练时再增加对应练习。

这是规划技能。制定计划不自动授权执行其中的实验、安装依赖、调用付费模型或部署系统。当前请求若同时包含实施，则按其授权范围执行。

## 形成计划

### 1. 确定学习约束

复用对话中的目标项目、基础、学习时长、日投入和期望成果。缺失信息仅在会影响安排时澄清，否则说明合理假设。不要把两天、全脱产或 Pi 固化为所有计划的前提。

默认用用户的语言交付。优先更新用户指定的原文件；未指定路径时，在当前工作区生成名称清晰的 Markdown 计划。

### 2. 先核对项目，再组织主题

优先查本地 README、架构文档和目标主题文档，必要时定位关键接口与实现。检查实际入口、模块职责、版本和实验性路径，给出可追溯的资料入口。避免用整仓库逐行阅读代替问题驱动的核对。

区分：

- 当前默认路径已实现的能力。
- 可由扩展或外部组件提供的能力。
- 学习者拟新增的设计。
- 尚未确认或尚未运行验证的内容。

文档声明、源码判断和实验结果分别记录。没有发现证据时描述检查范围，不把未知写成绝对不存在。不要把实验分支或第三方能力归给默认产品。

### 3. 选择贯穿案例

选一个与用户目标相关的小型应用作为贯穿案例，例如项目学习助手、内部知识助手或任务执行服务。每个主题都回答：原项目已提供什么，需要补什么，由哪一层负责？

案例用于推导架构与验证假设，不默认要求学习者完整开发一个产品。

### 4. 按设计问题安排模块

每个模块包含：工程问题、具体场景、现有设计、替代方案与代价、AI 辅助实验、学习者需作出的判断、成果与验收。

时间用于讨论、观察和评审；源码仅作为查证材料，通常占少量时间。学习时间充裕时增加失败场景、替代方案和迁移设计，不增加无目的的源码阅读量。

通用主题根据项目筛选：模块边界、数据流、状态归属、持久化、扩展、权限、可靠性、可观测性、成本及评估。Agent 项目另外覆盖下方专题。

### 5. 为每个模块设置观察活动

采用“提出问题 → AI 解释并查证 → 学习者预测 → AI 搭建实验 → 对比结果 → 作出设计决定”。实验优先复用现有入口或示例，只为关键假设生成最小代码。

列出输入、观察位置、判断标准和证据产物。模拟实验检验机制；真实模型实验检验决策和回答，不能相互替代。未运行的活动标记为计划，不声称验证通过。缺少环境时安排图解和待验证清单，不用模拟成功冒充系统边界已生效。

## Agent 项目的专题选择

### 整体架构与执行

区分模型、运行时、应用层、工具、存储和交互入口。说明谁决策、谁执行、谁保存、谁约束权限。用一次任务说明多次模型调用、工具批次、事件、追加指令与取消的关系。

比较单 Agent、固定工作流和多 Agent，依据任务分工与协调成本选择，避免仅凭技术名称分类。

### 上下文工程

分析每次请求实际包含什么：系统与项目指令、最近消息、工具定义、按需读取资料、检索结果和摘要。研究选择、加载时机、预算、截断、压缩、来源保留和冲突处理。

实验可比较全量输入与按需读取、压缩前后关键事实保真。区分历史存储、实际模型输入和提供商缓存；费用或 token 无真实数据时标为估计。

### Memory

区分当前工作上下文、会话历史、固定指令文件和跨会话长期记忆。不能从聊天存盘推断出自动提炼、语义检索或纠错能力。

设计生命周期：候选信息、写入策略、来源与范围、检索、注入、更新、冲突、过期和删除。讨论用户/项目隔离及错误记忆修复。按数据与查询需求比较文件、结构化数据库和向量检索，不预设向量数据库为必要组件。

### 安全与隔离

核对项目实际安全模型，不假设它自带沙箱。区分提示约束、工具可用范围、执行前策略、资源加载信任和操作系统级隔离。

画出模型服务、主进程、扩展、工具环境、文件、网络与凭据的位置。比较整个进程隔离和仅工具隔离，分析宿主扩展、挂载目录和凭据注入带来的边界。

实验使用专用目录和假秘密。一次模型拒绝不能证明防住提示注入；策略钩子模拟不能证明系统级沙箱有效。外部环境是否可用单独核实。

### 可靠性、扩展与评估

区分模型失败、工具失败和副作用成功但结果未保存。讨论重试、超时、取消、幂等、预算和人工介入。会话恢复不自动等于任务事务恢复。

按职责比较提示模板、Skill、工具、扩展、SDK 和进程协议。观察调用关联、运行轨迹、成本、错误及记忆来源，日志考虑敏感数据暴露。

评估同时覆盖任务正确性和工程机制。以正常、资料不足、错误记忆、越权、工具故障和恢复等场景定义可观察标准。

## 交付结构与验收

按用户时间组织阶段，时长合计一致并留出休息。至少提供：

- 学习目标、coding agent 与学习者的分工。
- 项目架构地图及有选择的资料入口。
- 时间表和每模块的工程问题、观察活动、设计判断与验收。
- 可复制的提示词：架构解释、证据核对、实验委托、方案评审。
- 综合设计任务和产物清单。

最终成果优先是架构图、上下文策略、记忆生命周期、信任边界、失败处理表及架构决策记录。图文可由 AI 起草，学习者应能解释取舍、指出证据不足，并在新增约束下调整方案。

架构决策记录采用“问题 → 具体场景 → 候选方案 → 选择 → 代价 → 证据/待验证事项”。无需闭卷写代码。

交付前确认：没有残留手写实现要求；没有把研究计划表述为完成的实验；没有硬编码示例项目的能力为普遍事实；资料路径与本次检查一致。简短报告文件位置、重点和未验证范围。
