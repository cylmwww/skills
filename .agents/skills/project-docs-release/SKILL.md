# 项目文档与发布约定

目标：公开文档让读者理解并运行当前项目；内部材料保存设计、实施和验收过程。默认使用简体中文，用户指定的语言、文件名、位置和提交范围优先。

## 先确认实际范围

读取当前代码、配置、版本文件、README 和已有启动说明，区分已实现、已验证、历史结果与计划。以当前源码和本轮验证为准；历史记录只能作为标明日期/版本的历史证据。

用户只要求写方案或整理文档时，完成该范围并注明功能尚未实施；不能把文档任务扩展成代码实施、提交、推送或发布。用户已要求完成版本实施时，执行下面的交付顺序，不停留在方案。

## 面向首次读者的文档改写

用户要求 README、使用说明“面向第一次看到项目的人”，去掉开发/计划内容，或继续统一文档名称、入口与链接时，读取[公开文档改写流程](references/public-docs-rewrite.md)。仅改文件名时只执行命名、引用和检查部分，避免重写已认可的正文。

- 以当前源码、默认配置和真实入口核对文档，修正“未实现”等过时描述；模拟机制、真实调用、人工语义验收与部署状态分别表达。
- README 介绍目的、功能、入口、运行方法与必要的代码架构；主题文档解释对应操作，不承载阶段计划、验收流水或内部报告入口。
- 新文档按用途命名；已有文档仅在用户要求命名整理时重命名，并同步 README、文档及实际调用方的引用与锚点。保留代码、配置和数据契约所需的真实名称。
- 忽略规则按本次用户选择设置。changelog 可以公开，也可以经授权留本地；不要把这次项目的处理推广成默认忽略所有版本记录。取消跟踪保留本地文件，并核对其仍存在。
- 改写文档不包含删除测试、变更业务代码、迁移包名、改写机器数据、付费模型调用或自动部署。需要附带修改时先核对本次授权；用户取消的操作立即移出范围。
- 文档改写以链接、锚点、配置、命令参数与变更范围检查为主，不为此重跑昂贵业务或模型评测。仅在用户要求提交时提交；提交与推送分别核对授权，沿用本任务已有授权，不重复确认。

## 功能实施任务的交付顺序

下列顺序适用于包含功能实施的任务；纯文档整理完成相应文档检查即可，不额外制造实施记录或验收报告。

完成具体实现 → 执行验收并处理失败 → 写完本地验收报告 → 同步启动说明、README、版本记录 → 检查提交内容。

- 验收包含与变更相关的代码/接口/界面/迁移及回归；AI 功能分别记录机制测试、真实模型测试和人工复核。固定脚本演练、模型自评或页面可打开不能替代实际能力验收。
- 若部分验证无法完成，报告注明未验收项和原因，公开文档只写实际实现及已证实结果，不宣布全部通过。
- 公开文档与真实默认配置、版本号和启动参数一致；完成验收后再宣布新版本能力。产品版本与数据库迁移版本分开说明。

## README 写法

以本项目自身为主体，按需要介绍：产品定位和用户、当前版本功能、架构及核心链路、快速启动、演示流程、验证摘要、实际能力边界。

- 描述模块职责、数据流和设计取舍，不把原始项目介绍、继承/复用关系或迁移过程作为叙事主体。来源对比仅写在本地内部材料。
- 不添加实施方案、实现记录、验收报告的路径、链接或目录入口；目录树也不列内部档案。可链接公开的启动说明、版本记录和使用所需资料。
- 将计划与当前能力分开；不要把待实施能力写入“当前能力”。不把历史成绩当作本轮成绩，不虚构功能、指标、独立原创声明或已验证部署。
- 不因调整产品叙事删除 LICENSE 或必须保留的版权/许可信息。准确保留运行所需的包名和命令；若用户要求 README 不出现历史标识，优先使用已有有效启动脚本，不编造新命令或自行开展包名迁移。
- 快速开始使用可复现的配置和种子数据，不依赖开发者私有数据库、绝对路径或密钥；限制放在相关能力附近，避免面向读者堆砌内部实现记录。

## 启动说明写法

提供可复制的安装、配置、启动与验证命令，说明环境要求、模型/演练模式、必要账户或种子初始化、迁移要求、常见故障及恢复。

配置块明确标记占位值；不写真实密钥。使用实际存在的入口和参数，检查与 README 一致。启动说明必须能独立使用，不依赖被忽略的方案、报告或个人记录。

## 内部材料与本地存档

未另行指定时，实施方案、实现记录、验收报告及来源对比保存在仓库 `docs/local/`；原始运行结果和复核材料放在该目录的 artifacts 子目录。保留用户已指定的位置，并给这些文件设置精确忽略规则。

- 方案明确范围、基线、具体改动、依赖与阶段、验收方法和门禁，以及“实施完成后先写验收报告，再同步公开文档”的约定。阶段划分按任务规模决定。
- 实现记录写实际改动、关键决策、验证和剩余项；不伪装成已完成的验收结论。
- 验收报告写代码版本、环境、测试数据/模型、实测结果、首次失败与复测、人工复核、证据位置、未完成项和发布结论。记录用量和延迟时明确口径，不混淆模型调用与直接 API 用例。
- 本地存档不等于可保存秘密：不记录密钥或不必要的客户敏感信息。

## Git 隔离与提交检查

1. 检查已有 `.gitignore` 和 `git ls-files`。为 `docs/local/` 或指定文件添加忽略规则，避免使用 `/docs/` 这类会隐藏启动说明和公开资料的粗泛规则。
2. 对已跟踪且明确应留本地的文件，使用 `git rm --cached -- <精确路径>` 取消跟踪，保留工作区文件。仅新增忽略规则不能停止跟踪；不删除本地档案，不重写 Git 历史。
3. 提交前检查 `git status --short`、`git diff --cached --name-only` 和 `git diff --cached`。新增内部材料不得进入暂存区；旧档案取消跟踪产生的删除记录属于预期。代码、必要测试、可复现评测数据/脚本和公开文档可以提交。
4. 使用明确路径暂存，避免不加检查的全量暂存。数据库、密钥、原始模型响应、个人复核和本轮运行报告不随版本提交；用户指定其他范围时遵循其要求。
5. 区分文件已写、已取消跟踪、已提交、已推送；只有实际执行成功才能报告相应状态。取消跟踪不会清除远端历史，不承诺历史文件消失。

## 完成检查

确认公开文档中的命令、版本、功能和验证结论有依据；无内部档案入口或原项目叙事；本地文件存在且被忽略，公开资料仍可跟踪；相关 Markdown 链接和 Git diff 检查通过。

向用户报告交付文件、文档与 Git 隔离改动、验证结果和当前实施/提交状态。没有功能改动时，不为了文档整理重跑昂贵的全套业务或模型评测。
